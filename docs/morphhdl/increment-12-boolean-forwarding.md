# Increment 12: typed Boolean child-parameter forwarding

Increment 12 closes the Boolean half of named child-parameter forwarding. A
parent may now bind a child `BooleanParameter` from a typed `HdlBool`
expression without collapsing that expression to its default witness:

```scala
val routeEnabled = enable && (effectiveWidth >= limit)
emitInstance(
  name = "route_inst",
  moduleName = "BooleanRoute",
  booleanParameterBindings = Vector(
    parameterBinding("SELECT", routeEnabled)
  ),
  portConnections = connections
)
```

## Implemented surface

ParamRTL represents the association with a distinct
`BooleanParameterBinding(parameterName, value)` node. Integer and Boolean
associations remain different canonical kinds even though strict Verilog-2001
spells both as named `parameter integer` associations. Validation resolves the
binding target in the child Boolean namespace and analyzes the complete value
expression in the parent lexical scope. Integer-to-Boolean and
Boolean-to-integer binding-kind mismatches, duplicates and unresolved
references fail before target legalization.

The frontend overloads `parameterBinding` for `HdlBool`, retains every public
Boolean, public integer and local integer dependency, and accepts the result
only in the dedicated `booleanParameterBindings` collection of
`emitInstance`. The same identity, provenance and fail-closed rules used by
integer bindings apply; there is no conversion through Scala `Boolean`.

Morph default-shape recursion evaluates each Boolean binding against the exact
parent module-instance context. It then replaces the corresponding child
declaration default before recomputing child locals, widths, generate counts
and the default-selected generate-if branch. An unbound child parameter still
uses its own declaration default. This makes the concrete witness comparison
instance-aware when two instances of one child receive different Boolean
values.

The strict Verilog-2001 backend emits a normal named association whose value is
the legalized Boolean expression. Boolean references remain explicitly
integer encoded (`NAME == 1`); a non-literal binding is normalized to
`(boolean_expr) ? 1 : 0` so its association has the same target `integer`
shape as the child declaration. Comparisons and Boolean operators retain their
canonical precedence. Backend capability verification checks the full binding
expression, including subexpressions that are inactive under the default.

## Public contract fixture

`boolean_forwarding.v` is the eighth artifact generated by
`MorphContractFixtureGenerator` and `MorphVerilog`. Its fixed eight-bit
`BooleanForwarding` interface derives `EFFECTIVE_WIDTH = WIDTH + OFFSET`, then
forwards the nontrivial predicate
`ENABLE && EFFECTIVE_WIDTH >= LIMIT` to child Boolean parameter `SELECT`.
`BooleanRoute` uses one generate-if to select either `BooleanHighRoute` or
`BooleanLowRoute`. The two branches consume different parent inputs, so the
testbench checks behavior as well as hierarchy.

CI generates all eight artifacts in normal and reverse construction order,
requires an exact eight-file inventory and compares every byte with the
reviewed goldens. Verilator lints the default, disabled, below-limit and
inclusive-limit configurations. Icarus simulates all four without
SystemVerilog mode. Yosys independently proves the fixed ports, the exact
forwarded child hierarchy and the selected high/low leaf in every
configuration.

Positive orchestration tests cover bound true, bound false, an unbound child
default and a binding composed from parent Boolean, public-integer and
local-integer facts. Negative tests retain whole-design validation: an invalid
binding cannot be hidden in an inactive generate branch or by a default
Boolean result.

## Deferred by design

This increment does not add Boolean local parameters, multiple or nested
generate-if regions, generate-if/for nesting, `GenerateCase`, runtime
combinational or sequential processes, memories or guard-sensitive integer
interval refinement. A Boolean child binding changes compile-time parameter
context only; it cannot change public port presence or direction.

## Recommended next increment

Increment 13 should add identity-bearing Boolean local parameters. It should
provide deterministic dependency ordering and cycle rejection, preserve typed
Boolean expressions through child bindings and generate-if conditions, and
legalize them as strict Verilog-2001 `localparam integer` declarations. Nested
structural control flow and runtime processes should remain separate later
increments.
